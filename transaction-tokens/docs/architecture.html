aic-demos / transaction-tokens Proposed

The token that outlives no hop

An account-management portal built to draft-ietf-oauth-transaction-tokens-11. The manager's access token stops at the edge; a 60-second Txn-Token carries the authorized intent of one transaction across four services, and reaches the last one byte for byte identical to how it left the first.

The chain

What happens when a manager records an activity

  1. 1

    manager → AICSigns in. AIC issues an access token scoped portal.activities.

  2. 2

    manager → BFFPosts the activity: client, type, cost, date delivered, and a free-text note.

  3. 3

    BFF → TTSRFC 8693 exchange. request_details proposes the type, cost and date. The BFF is the only workload that ever sees the access token.

  4. 4

    TTS → AICIntrospects the subject token. Its real scope is the ceiling; if the scope cannot be determined, the request is refused rather than treated as unconstrained.

  5. 5

    TTS → AIC policyMay this workload request this internal scope, and assert these tctx fields? The BFF may assert a cost; the nightly job may not.

  6. 6

    TTSEnriches. The TTS — not the caller — decides what lands in tctx, adding a client tier and an approval flag nobody asked for.

  7. 7

    TTS → BFFReturns a signed JWT, typ: txntoken+jwt, good for 60 seconds, audienced to the trust domain.

  8. 8

    BFF → Activity APIWorkload identity in Authorization; the Txn-Token in its own Txn-Token header. Signature, audience and expiry checked before anything else happens.

  9. 9

    Activity API → LedgerThe same header, forwarded untouched. The ledger validates independently and reads cost and type from tctx — never from the body.

  10. —

    nightly job → TTSThe internally-initiated flow: no user token anywhere, a self-signed JWT as subject_token, and a policy that refuses it the fields the BFF is allowed.

Five processes, so a token can be watched crossing four boundaries. The portal is served by the BFF rather than run separately — one fewer process, and the draft has nothing to say about how the SPA is delivered.

Decisions

Three things worth arguing about

The TTS is ours, not AIC's

AIC's own token exchange is RFC 8693, and we already drove it in capability-tokens. It is the wrong tool here — for reasons that are properties of the product, not of our configuration:

  • requested_token_type cannot be the txn_token URN; AM issues access, ID and refresh tokens.
  • The typ: "txntoken+jwt" header is not settable.
  • A validate_scope script can read arbitrary request parameters — we proved that last time — but it cannot make AM emit a token of a different type.
  • audience is accepted and silently ignored unless a per-client flag is on; and even then the Txn-Token's aud must be a trust domain, not a registered client.

So the TTS is a small Fastify service — which is what the draft describes anyway. AIC's role stays real rather than decorative: it issues and introspects the manager's access token, which is what makes scope narrowing an actual constraint instead of theatre, and its policy engine is the issuance policy below.

The issuance policy lives in AM

The draft leaves “which workload may request which scopes, and assert which tctx fields” entirely to the implementer, and calls it the real access-control surface of the pattern. Encoding it as AM policies makes it Terraform-managed alongside everything else, and lets aic policy eval explain a refusal — which is worth a great deal in a demo whose whole point is legibility. Resource strings model each assertion: 

txn:scope:client:activity:write
txn:tctx:cost
txn:tctx:activity_type

with the requesting workload as the subject. “The BFF can assert a cost; the scheduled job cannot” becomes a policy diff rather than an if buried in the TTS.

The manager↔client relationship — measured, not guessed

You asked whether the policies could look in the app for the account manager↔client relationship, or whether IDM would be much easier. They turn out to be the same mechanism.

Probed live in bravo · 2026-08-28

A POLICY_CONDITION script's bindings are httpClient, logger, username, resourceURI, environment, advice, responseAttributes, authorized, realm, scriptName. There is no openidm binding — a policy cannot query IDM directly either.

And httpClient really does egress. A condition script fetched the tenant's own /am/json/serverinfo/* and https://example.com/, both 200, via new org.forgerock.http.protocol.Request(). The throwaway script, policy, policy set and resource type were deleted afterwards.

So both options are an outbound HTTP call from a Rhino script. The trade-off is not effort:

Relationship in the appRelationship in IDM
How the policy reads ithttpClient → activity-apihttpClient → /openidm/managed/…
Local developmentneeds a public URL for the appworks as-is; IDM is already public
Credential for the calla shared secret in an ESVa service-account bearer, also in an ESV
What it demonstratesa PDP consulting a business systemIDM relationships

There is a third option that avoids the egress entirely and is arguably the most faithful to the draft: the TTS resolves the relationship and enriches tctx with it, and the AM policy decides on the enriched claim. The draft asks the TTS to add a computed claim not present in the request anyway. The PDP then needs no callback, and AM is still the decision point.

The artefact

What actually travels

Amber marks the two claims the TTS added on its own authority. The free-text note is not here — it rides in the request body, where it cannot be mistaken for something integrity-critical. 

header{ "typ": "txntoken+jwt", "alg": "RS256", "kid": "tts-dev-1" }
payload{
  "iss":   "https://tts.acme-internal",      // optional in the draft; we set it
  "aud":   "acme-internal",                  // the TRUST DOMAIN, not a service
  "txn":   "01JG7Q4T2VYB8K",                 // one per business transaction
  "sub":   "am-alice",                       // the account manager
  "iat":   1787923140,
  "exp":   1787923200,                       // 60 seconds
  "scope": "client:activity:write",          // internal intent, NOT the portal scope
  "req_wl": "portal-bff",                    // the workload that asked

  "tctx": {                                 // the TTS is authoritative here
    "client_ref":    "client-4471",
    "activity_type": "advisory",
    "cost_cents":    45000,
    "delivered_on":  "2026-08-21",
    "client_tier":    "gold",               // enriched, not requested
    "needs_approval": true                 // enriched: cost > tier threshold
  },

  "rctx": {                                 // environmental
    "ip":     "203.0.113.7",
    "authn":  "pwd+otp",
    "portal": "acme-portal"
  }
}

Observability

The part that makes it a demo

Every hop logs the txn value, which workload it is, what it validated and what it decided — plus a hash of the token, never the token. A /trace/:txn view then renders the decoded payload at each hop side by side, so it is visually obvious that the same token traversed the chain unchanged. That side-by-side is the screenshot this POC exists to produce.

Honesty

Where this knowingly departs from the draft

  • No mTLS on BFF→TTS. The draft requires mutual authentication there, because the access token is in flight on that hop. We stub workload identity with a bearer and say so loudly in the README.
  • Static dev keys with a kid, committed and clearly marked as such.
  • One trust domain. No cross-domain chaining.

This list grows as we hit things; it is a deliverable, not an appendix.

Before building

Open questions

  1. Where does the manager↔client relationship live? App, IDM, or enriched into tctx by the TTS. The PDP-calls-the-app version is the most striking and needs a tunnel so AIC can reach it.

  2. Does the account manager sign in for real? The brief says stub the IdP — but AIC is right there and capability-tokens already has the journey plumbing. Real sign-in costs little and makes scope narrowing meaningful rather than theatre.

  3. Storage. SQLite via node:sqlite — zero dependencies on Node 22+ — unless you would rather see Postgres.

  4. Crypto and algorithm. jose, as in capability-tokens. RS256 with a static dev keypair, or ES256?

  5. Realm. bravo alongside capability-tokens, or its own?
