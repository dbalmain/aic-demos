aic-demos / transaction-tokens Built · running

The token that outlives no hop

An account-management portal built to draft-ietf-oauth-transaction-tokens-11, with AIC as the Transaction Token Service. The manager's access token stops at the edge; a 60-second Txn-Token carries the authorized intent of one transaction across three services, and reaches the last one byte for byte identical to how it left the first. Four things about the wire format the product cannot match, all of them labels — and a longer, more honest list of places where what is enforced here is narrower than what the draft describes.

The shape

Three services, one trust domain, one token

AIC is the Transaction Token Service: the exchange grant mints the token, a validate-scope script enforces narrowing, and a token-modification script assembles tctx and rctx. Bold edges carry the Txn-Token — minted once, and identical when it reaches the ledger.

The chain

What happens when a manager records an activity

  1. 1

    manager → AICSigns in for real. AIC issues an access token scoped portal.activities, stamped may_act naming the BFF — without which every exchange is invalid_request.

  2. 2

    manager → BFFPosts the activity: client, type, cost, date delivered, and a free-text note.

  3. 3

    BFF → AICRFC 8693 exchange. request_details proposes the type, cost and date; the BFF is the only workload that ever sees the access token.

  4. 4

    validate-scope → policyIs the requested internal scope within what the subject token actually carries? If the subject scope cannot be determined, refuse — never treat unknown as unconstrained.

  5. 5

    token-mod → IDMWhich client is this manager's, and what tier are they? Read in-process via the openidm binding — no outbound call, no tunnel. A client_ref the caller named that is not one of theirs fails the mint outright.

  6. 6

    token-mod → policyMay this subject assert a cost? An account manager's subject token carries portal.activities and may; the nightly job's carries job.accrual and may not. Then the script writes tctx — including two claims nobody requested.

  7. 7

    AIC → BFFA signed JWT, 60 seconds, aud set to the trust domain rather than a client id.

  8. 8

    BFF → Activity APIWorkload identity in Authorization; the Txn-Token in its own Txn-Token header. The calling workload is authenticated first; then signature, issuer, audience, expiry, the required claims and the operation scope — before anything else happens.

  9. 9

    Activity API → LedgerThe same Txn-Token header, forwarded untouched, alongside the Activity API's own workload credential rather than a replay of the portal's. The ledger validates independently and reads cost and type from tctx — never from the body.

  10. —

    nightly job → AICThe internally-initiated flow: no human, though there is still an AIC user record and an AIC-issued subject token behind it. It asks for a cost in the same exchange everyone else uses; the issuance policy declines, so the token it gets back simply has no cost_cents in it. One call, not two — nothing is retried. It records the cost-free entry, and the refusal is the demonstration.

Feasibility

What AIC can be made to do

Probed live in bravo on 2026-08-28 with a throwaway client pair and two throwaway scripts, all deleted afterwards and capability-tokens re-run to confirm the realm was left as found.

Works

request_details and request_context reach the script as requestProperties.requestParams.<name> — single-element arrays of strings, so JSON.parse(String(raw[0])). setField takes nested objects and they survive to the JWT, which is what makes a tctx-shaped token possible at all. And setField("aud", "acme-internal") works with the audience whitelist off entirely — the whitelist constrains the request parameter, not the claim.

The token-modification script has both an openidm and an httpClient binding, and a policy binding with evaluate. So enrichment and the issuance policy both happen inside the mint, which is exactly where the draft puts them.

Cannot — four wire labels

requested_token_type naming the txn_token URN is a hard invalid_request — the one extra parameter AM rejects, bisected one at a time against a working control. issued_token_type therefore reports access_token and token_type reports Bearer.

And the JWT header stays typ: "JWT". The context that would change it, OAUTH2_SCRIPTED_JWT_ISSUER, has schema metadata but no configuration hook anywhere in AIC.

These four are labels, and the mechanisms they name — narrowing, enrichment, propagation, per-hop validation, the issuance policy — are all intact, which is what makes AIC-as-TTS a trade rather than a fudge. They are not the whole list of departures, though; the honest one is at the foot of this page and is longer.

The trap worth designing around

setField coerces numbers to doubles, so a bare cost_cents claim emits 45000.0. Boxing with java.lang.Integer.valueOf helps only inside a nested object; at top level it is coerced anyway, and java.lang.Long and java.math.BigInteger are not reachable at all. 

accessToken.setField("tctx", { cost_cents: java.lang.Integer.valueOf(45000) });  // 45000
accessToken.setField("cost_cents", java.lang.Integer.valueOf(45000));            // 45000.0

Money lives in tctx, which is where the draft wants it anyway.

The relationship lives in AIC, not the app

The manager↔client relationship is a custom IDM managed object, related to bravo_user. The token-modification script's openidm binding reads it in-process — synchronous, no network call, no tunnel. This is a reversal from an earlier design: setup has to be a terraform apply plus a seed script, not "also stand up a tunnel."

Two traps to design around, both verified live: a custom property or reverse relationship added to a Ping-shipped object (like bravo_user) must be prefixed custom_ — not the realm prefix, not any other name — and comes back unindexed. And a relationship expansion via the openidm binding can read back empty for several seconds after a schema write, even though REST is correct the whole time — so a client_ref the caller named that does not resolve fails the mint, rather than being dropped while the token is minted anyway. (It was dropped, until an adversarial review found that a bogus client_ref plus a cost produced a costed token with no client on it.) A third: AIC does not synthesise the reverse side of a relationship — it has to be written onto the target object's own schema as a real second property. A policy-condition script has no openidm binding at all — probed the same day — so this trick is specific to the token-modification context.

The artefact

What actually travels

Amber marks the claims the TTS added on its own authority. The free-text note is not here — it rides in the request body, where it cannot be mistaken for something integrity-critical. 

header — typ is "JWT"; see Cannot, above{ "typ": "JWT", "alg": "RS256", "kid": "<realm signing key>" }
payload{
  "aud":    "acme-internal",                 // the TRUST DOMAIN, set by script
  "txn":    "01JG7Q4T2VYB8K",                // one per business transaction
  "sub":    "am-alice",
  "iat":    1787923140,
  "exp":    1787923200,                      // 60 seconds
  "scope":  ["client:activity:write"],       // internal intent, NOT the portal scope
  "req_wl": "TxnDemo_caller",                // the shared exchange client — see Departures

  "tctx": {                                // the TTS is authoritative here
    "client_ref":     "client-4471",       // vouched: the subject's own relationship
    "client_display": "Acme Holdings",     // vouched: enriched from IDM
    "client_tier":    "gold",              // vouched: enriched from IDM
    "activity_type":  "advisory",           // the caller's word, shape-checked
    "delivered_on":   "2026-08-21",         // the caller's word, shape-checked
    "cost_cents":     45000               // vouched: the issuance policy allowed it
  },

  "rctx": {
    "ip":     "203.0.113.7",
    "authn":  "pwd",
    "portal": "acme-portal"
  }
}

Two kinds of tctx field

Everything in tctx is bound to this one transaction under AIC's signature, so no hop can alter it. That is not the same as AIC having checked it, and conflating the two is how a pattern like this gets oversold. Vouched: the client fields come from IDM via the subject's own relationship, and cost_cents is there only because the issuance policy said so. Bound, not vouched: the activity type, the date and everything in rctx are the caller's own words — AIC validates their shape, rejects the request outright if it is wrong, and then binds them. It does not claim they are true.

Observability

The part that makes it a demo

Every hop records the txn value, which workload called it, what it validated and what it decided — plus a truncated SHA-256 hash of the token, never the token. GET /trail/:txn on the BFF then renders the decoded payload at each hop side by side, every column fetched from the service that produced it rather than reconstructed centrally, so the identical hash down the row is visible evidence that the same token traversed the chain unchanged. That side-by-side is the screenshot this POC exists to produce.

Nothing in a trail is a usable credential: a hash correlates, and a decoded payload carries no signature. The trails are in memory, capped, and each service's own /trail still sits behind the workload credential.

Two things the view is careful about, because the first version of it was evidence that could not fail. The green verdict requires all three hops to have reported — unreachable, non-200, unreadable and genuinely empty are four different states, and collapsing them into “no entries” meant stopping the downstream services left one surviving record, one hash, and a page announcing unanimity. And the “called by” line is labelled claimed, unverified: the shared workload credential cannot identify a caller, so recording an assumed one was worse than saying nothing — the nightly job calls the Activity API directly, and the trail used to attribute its requests to the BFF.

Honesty

Where this knowingly departs from the draft

This list used to have seven items and to call the first four "all of them labels". An adversarial review on 2026-09-01 found that materially incomplete: several of the differences below are reductions in what is actually enforced, not naming. Saying otherwise was the worst inaccuracy on this page.

Product limits, measured

  • Four wire labels — requested_token_type, issued_token_type, token_type and the typ header, listed above. We do send requested_token_type and audience, which the draft requires and AM accepts; AM simply answers the first with the access-token URN.

Deliberate reductions

  • No mTLS on the BFF→AIC exchange. The draft requires mutual authentication there, because the access token is in flight on that hop. We use client_secret_basic and say so.
  • Workload identity on internal hops is a shared secret, not SPIFFE or mTLS. It is a separate credential in Authorization, checked before the Txn-Token, so the draft’s requirement that a Txn-Token must not authenticate its bearer holds. It does not authenticate which workload: every service presents the identical value, so the ledger cannot tell the Activity API from the BFF, nor require that its caller was the previous hop. A separate shortfall from the req_wl one below — that is about who may MINT, this is about who may CALL.
  • One trust domain. No cross-domain chaining.
  • Signing keys are the realm’s, not TTS-specific — arguably better than the draft’s static-dev-keys concession, but not what it describes.
  • Enrichment data lives inside AIC itself (a managed object), not the app’s own database. The draft is silent on where a TTS gets it; keeping it in AIC means setup is a terraform apply, no tunnel.
  • The account manager signs in with the password grant. A real BFF uses authorization_code; nothing else in the pattern moves.

Where the authority is genuinely weaker than the draft’s model

  • req_wl does not identify the requesting workload. The draft defines it as the workload asking for the token, and expects the TTS to authorise that workload. Here the portal and the nightly job both authenticate the exchange as the single TxnDemo_caller client, so req_wl is TxnDemo_caller in every token and the issuance policy keys on the subject token’s scope instead. That is a design choice, not an oversight — one internal exchange identity, with the gate keying on the subject token’s own claims. It means this demo proves subject-dependent claim filtering, which is real and is what the refusal shows, and does not prove per-workload issuance control. Two related precisions: the subject token carries the transaction’s principal — in the human path, the account manager — not the workload that asked; and re-running the gate on every mint makes a POLICY edit immediate, while a scope already frozen into an issued subject token stays there until it expires.
  • The internally-initiated flow still mints an AIC user token first. The draft’s version has the job present a self_signed subject token with no user behind it. AM has no such token type, so the job signs an RFC 7523 assertion which AIC exchanges for an ordinary access token belonging to a seeded user record — and that is the subject token. No human, but not "no user token anywhere", which is what this page used to claim. The signing key is the install’s per-tenant key, shared with any other jwt-bearer use of the tenant.
  • Replay is bounded by lifetime and idempotent storage, not by single-use enforcement: a replayed token is refused with a 409 because the ledger’s primary key is txn, not because any hop tracks spent tokens. The draft leaves strict single-use optional. The 60-second lifetime was chosen, not measured.

This list grows as we hit things; it is a deliverable, not an appendix.
